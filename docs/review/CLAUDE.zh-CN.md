# COMP4020 作业 2

构建用户的课程网站，并如实记录开发过程。评分对象是部署后的网站；检查只能证明它实际检查的那些性质。

## 工作范围与信息来源

完成当前已经获得授权的任务。小而明确的修改不需要正式的规划流程。对于存在不确定性或影响多个部分的工作，先在 `PLAN.md` 记录目标、约束和验证方式。只有缺少的信息会实质影响结果，或某项操作尚未获得必要授权时才提问；与此同时，继续不依赖该回答的工作。只读请求不需要编辑文件、修改计划或提交 commit。

在阶段开始、范围发生变化以及交付时，按照 `docs/planning/requirements-audit.md` 重新核对在线作业说明、上游仓库和相关本地要求。先区分必须满足的要求与自行选择的增强项，再确定下一步工作的规模。

实现过程中始终遵循 `docs/planning/implementation-goals.md`。在恢复工作、到达里程碑或出现重要新证据时，审阅并完善它；把当前交接状态保存在 `PLAN.md` 中。先展示可以审阅的结果，等待学生反馈，再进入下一个设有审阅节点的阶段。

检查相关文件和 Git 状态。固定平台的信息由 `README.md` 负责保存；当前决策、已知失败和后续工作由 `PLAN.md` 保存。按任务需要读取资料，不要每次重新加载全部文档。复用仍然适用的证据。

- 涉及证据与作者身份的问题，查阅[考核规则](https://comp.anu.edu.au/courses/comp4020-agentic-coding-studio/topics/assessment/)和 [AI 使用政策](https://comp.anu.edu.au/courses/comp4020-agentic-coding-studio/topics/ai-use-and-integrity/)。

## 项目必须保持的约定

保留 `README.md` 规定的固定 Slop 身份标识、现有内容集合键名、构建流程和生成 API 的约定。使用平台支持的定制入口；增加内容或新集合，与重命名已有固定集合是不同的事情。保留分配给仓库的课程代码后三位；首位数字应与课程级别一致。修改教学日期时，同步修改受这些日期影响的内容。

保持 ID、关联引用和路由一致；链接要考虑站点基础路径。修改源文件，不要直接编辑生成的 `dist/` 文件。保护真正的要求，而不是测试中的错误：如果断言过强或有误，应依据要求以及合法、非法案例来纠正，不能只是为了掩盖失败而修改。

## 实现与审查

保留无关工作的修改，沿用项目现有模式。验证真实的输入边界，保留有用的错误信息；避免推测性的抽象、静默回退、过于宽泛的异常捕获，以及对 schema 已保证的数据进行重复检查。

对于新行为或缺陷，先复现有关问题，再做有针对性的修正并验证。用于保护现有正确行为的回归检查可以从一开始就通过。测试应接受合法的替代方案，并拒绝真正的缺陷。

有助于工作时，把独立研究或审查委派为范围明确的子任务；存在依赖的步骤按顺序推进。实质性修改需要独立审查，修复有证据支持的问题，并重新运行受影响的检查。请求的结果已经得到验证、重要问题已经解决后就应结束，不要仅为增加轮次而继续迭代。

在 `docs/IMPLEMENTATION-RESEARCH.md` 中记录重要来源、备选方案和实际观察到的结果。根据文件、来源或运行时证据核实审查者的判断。模型之间的比较不能证明真人偏好。把独特问题、决策和 harness 修订保存在 `docs/PROCESS-EVIDENCE.md`，附上实际检查、commit 链接和未解决的限制。

## 命令与验证

通过 `mise exec --` 使用 `mise.toml` 规定的版本；非交互式 WSL 否则可能选到较旧的系统 Node。

| 命令 | 作用 |
| --- | --- |
| `mise exec -- pnpm dev` | 在仓库的基础路径下启动源代码开发服务。 |
| `mise exec -- pnpm test` | 先构建生产输出，再运行 spec 测试。 |
| `mise exec -- pnpm check` | 类型检查、构建并运行 spec 测试。 |
| `mise exec -- pnpm check:evidence` | 检查提交证据和剩余 starter 内容。 |
| `mise exec -- pnpm preview` | 提供已有生产构建的预览服务。 |

运行与修改相关的检查；网站有实质性修改时运行 `pnpm check`。它已经包含构建：没有新的修改、失败或未解决的问题时，不要额外重复构建和测试。仅修改说明文字时，需要检查差异与一致性，不需要人为编造应用测试。

与记录下来的基线比较。尚未完成的验收要求，不等于新引入的回归，也不构成扩大任务范围的授权。保持已经通过的检查继续通过；提交前所有必需检查都要通过。

修改界面或导航后，使用 Chrome 兼容工具，在 1920×1080 和 390×844 两个尺寸检查构建后的网站，包括受影响的链接和控制台输出。重新构建后，要重新加载整个页面文档，并核实实际窗口尺寸，再比较截图。

对于页内导航，检查激活后的目标是否可见、键盘焦点是否正确，以及手机菜单的状态。增强导航时，保留原生跳过导航链接和浏览器历史行为。对于带有交互增强的内容，除了查看稳定后的页面，也要检查第一个可用画面、减少动态效果设置以及 HTML 回退内容。

对于内嵌幻灯片，检查真实的框架边界、切换后隐藏页面的焦点行为，以及浏览器脚本错误；收到就绪信号或 MDX 构建成功，并不能证明幻灯片可用。当 Markdown 中包含交互代码时，同时检查生成后的脚本和源代码。

提交前，阅读几个不相邻的教学周、一份考核说明和一套幻灯片。无法进行浏览器验证时应如实报告；构建通过或模型审查都不能证明课程吸引力、视觉质量或课程整体连贯性。表现一个有辨识度的对象时，先查看第一手视觉参考，再比较渲染结果的轮廓、比例与材质，然后交给真人审阅。

## 写作、证据与交接

面向学生的文字应直接、具体。保留用户的语气和任务范围；去掉泛泛的营销话术、不必要的免责声明，以及无关的实现细节。影响读者理解或决策的必要限定仍应保留。

说明过程时，写清具体要求、观察到的结果，以及由此作出的修改。通过这个例子解释专业术语。

从课程设定的 2035 年历史视角写教学页面。要求学生分析之前，先介绍陌生事件和术语；实际作品来源与编写范围的限制，保存在链接到的来源说明中。区分案例叙述报告的内容、学生的推断和课堂提出的方案，不要编造档案记录。

每个单元都应把有顺序的课前准备、有明确时间安排的课堂、具体产出和考核衔接起来。验证第一个行动入口，以及跨周的资料链接，而不只是资料分类。在接受总览页面之前，用手机尺寸检查新学生的首个操作入口，以及返访学生的周次选择器。必读材料应能在站内直接阅读，并能定位到具体段落。记录重要选择并核实引用；不要编造阅读材料、结果或反馈。

`PROCESS.md` 必须如实反映学生本人的工作与判断。收到请求时，可以帮助整理 commit 证据，并忠实地根据学生提供的笔记起草或编辑。缺少个人判断的理由时应询问，而不是编造经历或自行填满模板。A2 没有另外一份 reflection。

在有意义的实现节点，把决策、修改、实际检查、剩余问题和下一步行动记录到 `PLAN.md`。研究细节和完整对话不要塞进这份长期规则文件。发现重复出现的实际失败后，再新增或完善规则，并移除已经被替代的指导。

检查差异，并在获准的实现工作中形成连贯的本地 commits。不要让凭据出现在输出或受版本控制的文件中。保留权限设置；手动修改个人配置、引入新服务、推送、发布、修改仓库可见性和课程 ship 流程，都需要明确授权。报告结果、实际执行的检查，以及仍然重要的限制。
